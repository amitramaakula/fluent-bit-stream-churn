# Delayed logs: a diagnostic checklist

This is an operational decision aid derived from the measured Fluent Bit/CloudWatch experiments. It is not a claim that every late log has the same cause.

1. **Measure arrival, not just collector health.** Give test records stable IDs and timestamps. Compare creation time with first ingestion time, count missing IDs and distinguish repeated deliveries from duplicate read results. A running Pod does not establish fresh delivery. Keep input volume, record size and source schedule visible.
2. **Identify the API that is failing.** Separate `CreateLogStream` throttling responses from `PutLogEvents` errors and credential/network failures. Compare AWS call/throttle metrics with collector logs. One-minute account/region metrics can mix applications and experiment phases; do not attribute a mixed minute entirely to one design. A missing metric datapoint alone is not evidence of zero throttles.
3. **Turn the naming template into demand.** List every changing field: Pod name, node name, container ID or collector generation. Estimate new destinations per second across all writers sharing the account and region. For example, 100 clusters each requiring one new stream per second need 100 creation operations per second before retries. This is arithmetic, not a measured fleet test. Compare with the account's applied quota; different log groups do not create separate API quotas.
4. **Protect the backlog during recovery.** Inspect the collector's retry, buffering and storage limits. Avoid discarding buffers. Check whether a restart would change destination names and add creation demand. Our stress run did not test collector restarts, durable recovery through failure, or the benefit of changing worker counts. Do not assume a restart or extra workers resolves a quota bottleneck.
5. **Choose the smallest useful set of destination dimensions.** Keep separate policy boundaries in log groups. Use source-specific streams when direct navigation is valuable and creation demand is acceptable. Consider stable shared partitions when names change rapidly; stage startup creation or evaluate an applied quota increase when appropriate. Only naming reuse was benchmarked as a remedy here; precreation and quota changes remain options to validate.
6. **Test source retrieval before changing naming.** Preserve cluster, namespace, Pod name and UID, container name and record ID. Example CloudWatch filter: `{ $.kubernetes.pod_name = "checkout-old" }`. In a multi-cluster group, qualify the cluster and namespace or UID to avoid name collisions. Inspect both missing and unexpected records. We verified a replaced Pod's complete 20-record set from reused streams.
7. **Check initialization and replay.** A fixed set of 32 possible streams still needs first creation. Several writers can make redundant attempts; changing the partition count or scope can create new names. After recovery, audit unique record IDs: a partially delivered batch can be retried and resend accepted records. Our local three-record test demonstrates this without assuming exactly-once delivery.

The choice is conditional. Reuse trades direct stream-per-source browsing for field-based search and mixes multiple sources within a stream. Partition skew, ordering requirements, metadata gaps, startup, access/retention boundaries and query cost need workload-specific evaluation. Neither 32 partitions nor a 99% latency reduction is a universal recommendation.

## Review a naming configuration against lifecycle events

Use one real collected record and its input configuration:

1. **Resolve the input identity.** Record the actual source filename and expanded tag. Our verified CRI path contains Pod name, namespace, container name and runtime container ID. A fixed input tag discards the filename boundary; `kube.*` retains a source-file boundary in the tested tail input.
2. **Trace transformations.** Inspect filters and record accessors. Determine which filename fields survive, which are removed, and whether a collector hostname is added. Do not assume that every input filename becomes a destination name.
3. **Apply the final template.** Calculate the exact (log group, stream) pair before and after each event. For example, Pod-plus-container-name stayed stable through the tested application container restart, while the full filename changed. Collector-plus-file names changed when the collector Pod was replaced, even though application files stayed unchanged.
4. **Count distinct pairs and attempts separately.** Replacing a collector routing twelve files changed twelve collector-plus-file destinations in the local mapping; collector-only naming changed one. A collector container restart preserved the tested collector-Pod-name keys. Cache loss can still cause repeated API attempts for unchanged names; that is a separate measurement, not new cardinality.
5. **Inspect chunk boundaries.** If an input chunk can route records to several destinations, one late creation failure can replay earlier accepted records. A per-file input boundary changes that failure surface. Do not assume that the earlier mixed-destination retry demonstration predicts duplicates for every file-tailing configuration.

The [verified lifecycle matrix](RESULTS.md) covers application container restart, application Pod replacement, collector container restart and collector Pod replacement. Log rotation is excluded. It is a configuration-review method, not a list of universally unsafe fields or a claim about AWS defaults.
